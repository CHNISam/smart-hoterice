## 2. 项目背景

### 2.1 背景说明

SmartRice Platform 是一个面向传统米业企业的轻量化数字服务平台，目标是在不脱离企业现有经营方式的前提下，将原本依赖电话沟通、人工登记、人工分流和人工回访的业务流程逐步整理为更清晰、更可追踪的线上承接流程。

企业并非从未尝试线上化。早在约2010年，企业就曾通过电视广告等方式开展远程销售；到2025年，企业也已在拼多多等平台上架商品。这说明企业一直存在拓展线上渠道、扩大销售范围、提升订单承接效率的现实需求。

但已有渠道更多解决的是"订单入口"问题，并没有真正解决"订单承接后如何统一整理、如何分流、如何配送、如何回收反馈"的问题。尤其在大米这类单件重量较大、配送成本敏感、履约依赖线下组织的业务中，如果订单、地址、服务归属、支付方式与配送安排不能被结构化整合，企业就很难持续优化配送效率与运费成本。

与此同时，用户在购买后也缺少统一、方便、可沉淀的反馈入口，企业难以及时收集产品体验、服务评价和异常问题，导致后续运营优化缺乏依据。

因此，本项目希望围绕"客户连接、订单承接、分拣建批、司机配送、异常回访、用户反馈"构建一个轻量但完整的数字服务闭环，为企业后续更稳定的数字化运营打下基础。

### 2.2 为什么现在做

1. 企业已有线上销售尝试，但缺乏统一承接与履约闭环。
2. 配送成本与人工组织成本压力较高，需要更清晰的订单聚合与分流机制。
3. 毕设项目需要围绕真实业务问题落地，而非停留在通用商城展示层面。
4. 微信小程序形态更适合客户下单、司机执行和轻量化企业协同。

## 3. 产品定位

### 3.1 产品定位

SmartRice Platform 是一个面向传统米业企业的轻量化数字承接平台。它不是一个重型ERP，也不是通用大型电商平台，而是围绕实际业务流程，重点解决客户下单、服务点承接、订单聚合建批、司机履约执行与反馈沉淀的问题。

### 3.2 产品形态

产品包含三类端：

1. **客户端小程序**：面向外部客户，用于查看商品、选择服务点、下单、查看订单、接收通知和提交评价。
2. **司机端小程序**：面向配送司机，用于查看批次任务、执行配送、处理异常和展示统一收款码。
3. **后台管理端**：面向企业内部员工，用于商品管理、订单管理、司机管理、批次调度、经营分析和系统配置。

### 3.3 产品边界

本项目当前阶段的系统边界如下：

- 支持客户选服务点、下单、查看订单、评价与通知。
- 支持司机查看批次、执行配送、上报异常、展示统一收款码。
- 支持后台进行商品管理、订单承接、司机管理、批次调度与轻量经营分析。
- 支持扫码支付与货到付款两类结算方式。
- **当前不接入库存系统，不实现复杂库存联动与库存预警**。
- **AI 仅作为只读辅助解释与分析能力，不直接修改业务状态**。

## 4. 目标用户

### 4.1 客户

面向企业外部客户，主要使用场景包括：

- 浏览商品
- 选择服务点

- 发起下单

- 登录司机端

- 查看批次详情与订单详情
- 导航到客户地址
- 一键拨号联系客户
- 标记送达或异常
- 向客户展示公司统一收款码

### 4.3 企业员工

面向企业内部运营、客服、调度等人员，主要使用场景包括：

- 管理司机信息
- 进行订单分拣、聚合与建批
- 跟踪配送异常与回访结果
- 查看基础经营数据

## 5. 核心痛点

### 5.1 客户侧痛点

1. 用户缺少统一的线上入口完成服务点选择、商品查看与下单。
2. 不同服务点承接规则不清晰，用户难以判断是否支持平台送货。
3. 用户购买后缺少便捷的订单查看、通知接收和反馈入口。
4. 用户对货到付款是否可用缺少明确约束与提示。

### 5.2 企业侧痛点

1. 订单信息分散，难以及时集中掌握。
2. 地址数据、服务归属和配送信息缺乏结构化整理。
3. 零散订单难以形成可执行配送批次，履约成本高。
4. 配送异常缺少清晰闭环，后续跟进不直观。
5. 用户反馈缺少沉淀入口，运营改进缺乏依据。

### 5.3 司机侧痛点

1. 司机需要快速看到可执行批次，而不是在零散订单中自行判断。
2. 配送过程中需要快速导航、拨号和异常上报入口。
3. 线下收款需要统一标准展示方式，避免流程混乱。

## 6. 产品目标

### 6.1 业务目标

1. 建立企业统一的客户线上承接入口。
2. 将订单数据、地址数据和服务点归属进行结构化沉淀。
3. 支撑订单从承接到配送执行的闭环流转。
4. 通过分拣建批能力为配送效率优化提供基础。
5. 为后续配送成本控制与运营分析提供数据基础。

### 6.2 用户目标

1. 让客户可以更方便地下单、查看状态和提交反馈。
2. 让司机可以更高效地执行配送任务。
3. 让企业员工可以更清晰地进行订单承接与调度。

### 6.3 产品目标总结

本产品的目标不是做一个大而全的商城，而是围绕传统米业企业的真实业务，将订单承接、分拣聚合、配送执行和反馈回流这几件最关键的事情做清楚。

## 7. 产品原则与红线

### 7.1 核心原则

1. **Prototype-first**：优先对齐原型。
2. **Spec-Driven Development**：先明确做什么和验收标准，再实现。
3. 一次只做一个明确feature，不发散。
4. 不擅自改变业务流程和业务定义。

### 7.2 验收红线

1. 全中文UI，不得出现英文token。
2. 确认下单页不直接出现线上支付按钮成功态表达。
3. 线下当面收款由司机展示统一收款码，不做司机端在线收款。
4. 定位权限仅在需要推荐附近服务点时请求。
5. 服务点只能在"服务点"入口选择/切换。
6. 经销商场景下不生成平台配送订单。
7. 当前阶段不引入库存系统表达。

## 8. 双智能助手概述

### 8.1 产品定义

SmartRice 智能助手不是单一聊天功能，而是一个多端共享底层能力、前台分场景呈现的**双助手体系**：

#### 8.1.1 C端助手

- **覆盖**：微信小程序、PC商城
- **定位**：购米决策助手、规则解释助手
- **目标**：帮用户更容易选米，帮用户理解商品差异、适用场景、配送/自提/售后规则，降低咨询成本，提升下单前决策效率

#### 8.1.2 B端助手

- **覆盖**：管理后台
- **定位**：业务知识问答助手、规则/流程解释助手
- **目标**：帮内部人员快速理解后台流程、服务点规则、配送链路、售后逻辑、配置说明，提供可追溯答案，支撑测试、培训、验收与毕业设计演示

### 8.2 产品背景

当前系统已有AI助手demo和知识库管理能力，但离正式产品仍有明显差距：

- B端已有demo，但回答稳定性、知识边界、来源归因、检索污染控制仍不足
- C端尚未形成完整"选米 + 规则解释"的产品闭环
- 目前仍缺少统一的查询分流和场景化回答策略
- 仅靠手工随意提问无法有效评估RAG质量

**RAG的行业最佳实践并不支持"把所有文档丢进去，再靠模型自己想办法"**。OpenAI的Retrieval指南明确支持按attributes做过滤；Anthropic的Contextual Retrieval强调检索阶段本身需要优化；LangSmith和Google的资料都强调先建立评测集，再对检索链路和回答链路做针对性迭代。

### 8.3 产品目标

#### 8.3.1 C端目标

- 让用户更快选到合适的米
- 降低"我该买哪种"的决策成本
- 用更自然的问答方式解释商品和规则
- 在不增加太多客服成本的前提下，提升自助咨询体验

#### 8.3.2 B端目标

- 让内部人员更快理解平台规则和业务流程
- 降低培训、查文档、解释规则的成本
- 让答案具备可追溯性和演示价值
- 让系统成为毕设中的一个完整AI子模块，而不只是聊天框demo

#### 8.3.3 技术目标

- 形成统一知识底座
- 形成多端分层输出
- 支持轻量但可维护的RAG流程
- 建立最小评测与回归机制

### 8.4 非目标

本期不做：

- 通用闲聊机器人
- 企业BI/经营分析助手
- 自动执行后台操作的agent
- 多租户知识平台
- 复杂权限体系
- **实时库存、实时优惠、实时订单、实时经营数据问答**

> **决策**：C端不允许回答实时数据边界问题。这类问题高风险、高维护成本，而且对毕设收益低。OpenAI建议在高不确定性场景下通过约束回答边界、过滤上下文和建立清晰路由来控制错误。

### 8.5 产品原则

1. **双助手，共底座**：底层共享知识入库、切分、索引、检索、评测能力；前台按C/B端做差异化展示。

2. **有依据才回答**：回答优先基于检索结果，而不是自由发挥。RAG的核心价值就是grounded answer。

3. **简单问候允许，闲聊不做**：允许简单问候，但不闲聊。系统可以礼貌回应，但不会进入陪聊模式。

4. **模糊问题优雅处理**：
   - 问候类：直接礼貌回应
   - 低信息量但疑似业务类：先澄清
   - 明确业务类：检索后回答
   - 超边界类：明确说明边界并引导
   
   这类query routing / query transformation是主流RAG优化方向之一。

5. **轻量知识治理，逻辑自洽**：默认知识库里不会乱放无关东西，保持轻量、自洽。不强调重型知识权限体系，而是强调：
   - 文档来源可控
   - 内容范围清晰
   - 场景标签清楚
   - 默认数据集干净

## 10. 知识体系设计

### 10.1 知识分层

| 类别 | 内容 |
|------|------|
| **A. 商品知识** | 商品介绍、品类差异、适用人群、适用场景、口感/用途、推荐理由 |
| **B. 交易与履约知识** | 下单流程、支付方式、配送规则、到店自提规则、服务点规则、售后规则 |
| **C. 平台与后台知识** | 后台页面说明、批次调度规则、状态流转规则、操作说明、配置逻辑 |

### 10.2 场景映射

- **C端优先使用**：A + B
- **B端优先使用**：B + C

这个"共享底座、场景分流"的方式，比让所有端共享同一提示模板更稳，更符合多场景RAG实践。

## 11. RAG方案要求

### 11.1 文档支持

支持：

- PDF
- Word
- Markdown
- Excel

### 11.2 Chunking规则

| 格式 | 规则 |
|------|------|
| Markdown | 按标题层级切 |
| Word | 按标题 + 段落切 |
| PDF | 尽量保留页码、章节、标题 |
| Excel | 按表头 + 行内容或规则块切，不整表一坨 |

> Google和OpenAI相关资料都指出，chunking方式会显著影响召回质量；PDF/表格更需要定制切分而不是一刀切。

### 11.3 Metadata要求

每个知识片段至少包含：

- 文档名
- 文档类型
- 知识类别
- 适用场景（C/B/通用）
- 标题/章节
- 页码/行号（可取则取）
- 上传时间
- 启用状态

> OpenAI Retrieval指南明确支持attribute filtering，这类metadata不是装饰，而是检索控制的重要基础。

### 11.4 Query Processing

问题进入后先分类：

- 问候
- 选米咨询
- 规则咨询
- B端业务问答
- 模糊问题
- 实时数据问题
- 非业务问题

再决定：

- 固定回应
- 澄清
- 检索后回答
- 拒答/引导

### 11.5 Ranking / Filtering

本期采用轻量但有效的策略：

- 场景标签过滤
- 启用状态过滤
- 类别优先级
- 结果去重
- 低质量命中剔除

> Anthropic明确指出，只靠朴素向量召回会产生较多失败，结合上下文和重排能显著降低失败率。本期不一定要上复杂reranker，但PRD应预留这个方向。

## 12. 模糊问题处理策略

### 12.1 问候类

例如：

- 你好
- hi
- 在吗

**处理**：礼貌回应 + 给出建议提问方向 + 不进入闲聊

### 12.2 模糊但疑似业务类

例如：

- 配送
- 规则
- 论文
- 这个
- 那个

**处理**：优先澄清 + 不直接强答

### 12.3 明确业务类

**处理**：直接进入检索与回答

### 12.4 超边界类

例如：

- 今天库存多少
- 现在优惠多少
- 这个月订单数据怎么样

**处理**：明确不支持当前实时数据问答 + 引导查看后台/活动页/人工确认

## 13. 思考过程 / 检索依据展示策略

### 13.1 C端

- 不展示思考过程
- 不展示技术性检索依据
- 只展示用户需要的结论与推荐卡片

### 13.2 B端

- 展示检索依据与来源
- 展示思考过程/回答分析
- **默认折叠**

这个分层兼顾了用户体验和内部可解释性。LangSmith的可观测性资料也强调，内部traces和外部展示应该分层，而不是原样暴露所有中间过程。
